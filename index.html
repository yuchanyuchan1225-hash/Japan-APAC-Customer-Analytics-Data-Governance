Customer analytics · data governance · lifecycle measurement

顧客ライフサイクル分析を、意思決定に耐える定義へ。

注文データを集計するだけでは、初回購入・継続購入・顧客数を正しく把握できない。注文粒度、顧客識別、観測期間、例外処理を先に定義し、分析結果を業務で使える状態へ整えた方法論ケース。

01 / Business problem

集計はできても、比較可能な顧客指標になっていない。

01

商品行と注文行の混在

同一注文に複数の商品行があると、注文金額を商品行のまま合計した時点で二重計上が起こり得る。

02

顧客 ID の断絶

ゲスト購入、会員登録、メールアドレスの揺れが混在すると、同一人物を別の顧客として数える危険がある。

03

業務例外の誤読

取消、社内利用、特典、配送条件を通常購入と同じ扱いにすると、傾向と運用上の例外が混ざる。

02 / Analytical definitions

F1 と F2 は、ラベルではなく定義である。

F1 は観測期間内の最初の成立注文、F2 は同じ顧客の2回目以降の成立注文として扱う。これは「生涯で初めての購入」を示すものではない。

論点 曖昧な扱い 公開ケースで採用する扱い
初回購入 過去すべての履歴を持たないまま「新規」と呼ぶ 観測期間内の初回と明記する
F1 / F2 の人数 同じ月に両方へ現れる顧客を単純加算する 顧客数の合計はユニーク ID で再計算する
キャンセル注文 購入回数として F1 / F2 に含める 成立注文と分離し、必要な場合のみ別の運用指標として扱う
リピート顧客群 顧客群の総売上を F2 売上と呼ぶ 注文レベルの F2 と、顧客群の貢献を別指標にする
03 / Data governance

分析の前に、データの通り道を整える。

01 原データを確認 レコード粒度、状態、必須項目、抽出期間を確認する。
02 注文単位へ正規化 商品行を注文代表行へ整理し、金額・状態の二重計上を避ける。
03 本人性を解決 会員 ID とゲスト情報を、根拠を残して分析用キーへ接続する。
04 ライフサイクルを付与 成立注文の時系列だけで F1 / F2 を付ける。
05 検算と解釈 集計値を照合し、例外・限界・誤用しやすい表現を明記する。
04 / Synthetic example

数字を見せるためではなく、誤った結論を防ぐための比較。

合成例
ある月に F1 が 120 人、F2 が 18 人でも、18 人のうち 6 人が同月に初回注文と再注文を行っている場合、月間ユニーク顧客数は 138 人ではなく 132 人になる。F1 と F2 の人数は、用途に応じて重複を処理する必要がある。

報告で守ること

「リピート顧客の売上」と「F2 注文売上」は別物。前者には、その顧客が過去に行った初回注文や取消注文が含まれる場合がある。指標名は計算方法と一致させる。

06 / Operational value

分析品質を、次の業務判断へつなげる。

CRM の対象設計

顧客を一意に扱える前提を整え、会員施策や再購入施策の対象定義を安定させる。

運用例外の管理

取消、社内利用、配送条件などを隠さず分離し、異常値と業務ルールを区別する。

説明可能な報告

数値の背景、限界、再計算条件を残し、担当者が変わっても同じ解釈へ戻れる状態にする。

06 / Ownership

分析結果だけでなく、使える定義と運用の土台をつくる。

Insight Ownership

注文・顧客データの不連続を分析課題として定義。F1/F2、顧客群、成立注文を混同しない指標体系を設計した。

Execution Ownership

データ確認、集計粒度の整理、本人性ルール、例外分類、QA、報告用の定義文書までを一連の分析プロセスとして構築した。

Ownership Boundaries

公開版は方法論と合成例のみを収録。実在する顧客、注文、企業、内部運用ルール、実績値は非公開とする。
